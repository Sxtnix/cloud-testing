## 1. CONTEXTO Y ARQUITECTURA EXISTENTE

El proyecto Pedidos360 es una tienda online desarrollada con una arquitectura Cloud Native basada en microservicios.

Tecnologías identificadas en el proyecto:

* Frontend: Angular 17 con componentes standalone.
* Backend: Java 17 y Spring Boot 3.2.
* Persistencia: Spring Data JPA y MySQL, según la configuración existente.
* Autenticación: Azure Entra ID y MSAL Angular.
* Mensajería: RabbitMQ.
* Correos: Spring Mail mediante SMTP.
* Contenedores: Docker y Docker Compose.
* Infraestructura prevista: AWS EC2 y API Gateway.

Actualmente existen cuatro microservicios:

**`ms-productos`**

* Catálogo de productos.
* Consulta de productos.
* Operaciones CRUD disponibles.

**`ms-identidad`**

* Perfil de usuarios.
* Integración con la identidad de Azure.
* Consulta de información del usuario autenticado.

**`ms-carrito`**

* Administración del carrito.
* Agregar y eliminar productos.
* Checkout.
* Generación de pedidos.
* Historial de compras.

**`ms-email`**

* Envío de correos mediante SMTP.
* Consumo de mensajes desde RabbitMQ.
* Envío asíncrono de confirmaciones de compra.
* Endpoint de envío manual para pruebas.

También existe un frontend Angular con estas páginas:

* Login.
* Catálogo.
* Carrito.
* Pedidos.
* Barra de navegación.

Respeta esta arquitectura y conserva los cuatro microservicios. No agregues un quinto microservicio sin una justificación técnica y académica clara.

## 2. OBJETIVO GENERAL

Completar y mejorar Pedidos360 para que funcione como una tienda online realista, moderna y demostrable.

El flujo principal esperado es:

1. El usuario accede a la tienda.
2. Explora el catálogo.
3. Inicia sesión.
4. Agrega productos al carrito.
5. Modifica las cantidades y revisa el total.
6. Continúa al checkout.
7. Selecciona un método de pago.
8. Confirma la compra.
9. Se registra el pedido.
10. Se procesa el pago simulado.
11. Se envía una confirmación por correo electrónico.
12. El usuario consulta sus pedidos y sus estados.

El sistema debe integrar correctamente frontend, backend, persistencia, autenticación, mensajería y notificaciones por email.

## 7. SISTEMA DE CORREOS ELECTRÓNICOS

**IMPORTANTE: ya tenemos implementado `ms-email`. No reemplaces este servicio ni crees otro sistema de correos paralelo.**

Actualmente:

* `ms-carrito` dispone de un `EmailPublisher`.
* RabbitMQ utiliza la cola `pedidos360.emails`.
* `ms-email` consume los mensajes.
* `EmailService` utiliza SMTP.
* Existe un endpoint manual `POST /emails/enviar`.
* Se publican confirmaciones de compra de forma asíncrona.

Primero audita esta implementación y verifica qué partes funcionan realmente.

Después, amplía el sistema para cubrir los nuevos eventos del proceso de compra.

Correos que deberían poder enviarse:

* Confirmación de compra.
* Confirmación de pago aprobado.
* Aviso de pago rechazado, si corresponde.
* Actualización de estado del pedido, cuando se implemente esa funcionalidad.

Evita enviar dos correos idénticos por el mismo evento.

Utiliza mensajes claros y profesionales, preferentemente con plantillas HTML sencillas si resulta compatible con la estructura actual.

Los correos deben incluir, cuando corresponda:

* Nombre del cliente.
* Número de pedido.
* Fecha.
* Detalle de productos.
* Total.
* Método de pago.
* Estado del pedido.

Mantén RabbitMQ como mecanismo de comunicación asíncrona.

El envío de correos no debe provocar que una compra ya registrada falle si el servidor SMTP está temporalmente fuera de servicio.

Revisa los logs, las excepciones, los reintentos y la configuración de la cola. Si es viable, mejora la gestión de mensajes fallidos mediante reintentos acotados o una cola de respaldo.

Las credenciales SMTP deben continuar utilizando variables de entorno y nunca deben quedar expuestas en el repositorio.

Documenta cómo probar los correos en un entorno local sin credenciales reales.
